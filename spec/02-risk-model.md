# 02. Risk Model

## 1. 设计原则

风险分析不是把文件数量加总，也不是让模型直接给一个分数。系统先记录变更事实，再识别信号，最后由策略引擎根据证据和缓解项计算风险。

一个风险结论必须回答四个问题：

1. 改了什么？
2. 可能影响什么？
3. 证据在哪里？
4. 合并前应该验证或补充什么？

## 2. 风险维度

| 维度 | 典型信号 | 优先关注 |
| --- | --- | --- |
| `security` | 权限、认证、输入、Secret、注入 | 身份边界、外部输入、敏感数据 |
| `data` | Schema、迁移、删除、兼容 | 回滚、数据丢失、旧版本兼容 |
| `api` | 路由、公开函数、协议、序列化 | 客户端破坏性变更 |
| `reliability` | 超时、重试、资源释放、错误处理 | 故障放大和恢复能力 |
| `concurrency` | goroutine、channel、锁、共享状态 | 竞态、泄漏、死锁 |
| `performance` | 热点循环、批量查询、缓存 | 延迟、吞吐、资源消耗 |
| `delivery` | Workflow、镜像、配置、部署 | 权限、发布顺序和环境差异 |
| `supply_chain` | `go.mod`、Action、镜像依赖 | 来源、版本、供应链变化 |
| `testability` | 关键逻辑无测试、迁移无验证 | 能否证明变更安全 |

## 3. 严重级别

### `critical`

可能导致严重安全事件、数据不可逆损坏、生产大范围不可用或供应链接管，且变更中存在直接证据。默认只报告，不阻塞。

### `high`

可能导致重要功能错误、权限绕过、数据兼容失败、资源持续泄漏或部署事故，需要合并前人工确认或补充测试。

### `medium`

有明确影响面，但存在缓解措施、影响范围有限或证据仍需要验证。

### `low`

风险较小、主要是可维护性和验证建议，不应制造大量噪声。

### `needs_review`

模型或规则发现了线索，但证据不足以支持 `medium` 以上结论。它不是严重级别，而是证据状态。报告必须同时保留原始线索和缺失的验证项。

## 4. 证据要求

每个 `high` 或 `critical` finding 必须至少包含：

- 具体文件路径。
- 可定位的新增或删除行范围，或者明确的文件级证据。
- 变更前后事实。
- 影响解释。
- 建议的验证或修复动作。
- 规则 ID 或模型分析来源。

以下内容不能单独作为高风险证据：

- 只说“可能有问题”的一句话。
- 没有文件路径的模型判断。
- 只引用 PR 标题或正文。
- 只因为文件很大、代码很复杂或使用了某个框架。
- 只因为静态工具没有运行。

## 5. 确定性评分

定义总分为 0 到 100。模型不能直接写入 `score`，只能贡献经过证据校验的候选信号。

```text
raw_score = Σ(signal_weight × evidence_factor × exposure_factor)
mitigated_score = max(0, raw_score - Σ(mitigation_credit))
final_score = min(100, mitigated_score)
```

建议因子：

- `signal_weight`：规则本身的风险权重，范围 1 到 40。
- `evidence_factor`：有行级事实为 1.0，文件级事实为 0.7，只有模型线索为 0.3。
- `exposure_factor`：公共接口、生产配置和权限路径可以提高到 1.0；内部实验代码可以为 0.5。
- `mitigation_credit`：已有测试、回滚脚本、权限收窄和显式超时等可以降低分数，但不得把确定的安全漏洞抵消为 `low`。

初始等级阈值：

- `0-24`：`low`
- `25-49`：`medium`
- `50-74`：`high`
- `75-100`：`critical`

阈值只是初始配置，必须通过 fixture 评测后再调整。

## 6. 规则示例

### 6.1 Workflow 权限扩大

- 事实：workflow 从 `contents: read` 变为 `contents: write`，或增加写权限。
- 基线：`high`。
- 加权：如果同时修改了 Action 引用或执行不可信输入，提升为 `critical` 候选。
- 证据：workflow 文件和权限块的新增行。
- 建议：说明为什么需要写权限，改为 job 级最小权限，并固定第三方 Action SHA。

### 6.2 公共 API 删除或签名改变

- 事实：公共路由、导出函数、协议字段或序列化结构发生破坏性变化。
- 基线：`high`。
- 证据：接口声明、路由表或 schema diff。
- 建议：兼容旧字段、增加迁移期或补充消费者测试。

### 6.3 数据库迁移删除列

- 事实：迁移中删除列、表或不可逆数据转换。
- 基线：`high`。
- 加权：没有回滚或双写策略时提高分数。
- 证据：迁移文件的具体操作。
- 建议：拆成 expand/contract 两步，验证备份和回滚。

### 6.4 Go HTTP 请求无超时

- 事实：新增外部 HTTP 请求但没有 `context` deadline 或 `http.Client.Timeout`。
- 基线：`medium`，在服务入口或高并发路径为 `high` 候选。
- 证据：请求创建和调用位置。
- 建议：增加超时、取消传播和失败重试边界。

## 7. 合并门禁

MVP 默认不阻塞合并。后续启用门禁时必须同时满足：

- 策略配置显式开启。
- finding 具有合法证据。
- 规则或模型在评测集上达到约定 precision。
- 报告状态不是 `degraded`，除非策略明确允许。
- 不以单个低置信度模型 finding 阻塞合并。
- 门禁结果能通过报告和日志复现。
